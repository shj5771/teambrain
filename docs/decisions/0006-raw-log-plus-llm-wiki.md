# 0006. 원본을 남기고, 위키는 AI가 정리한다

- 상태: 채택

## 상황

팀 기억을 어떤 모양으로 쌓을지에 대해 초안이 네 개 나왔다.

| 초안 | 방식 |
|---|---|
| A | 결정·사실·할 일·노하우의 네 가지 유형으로 추출하고, 임베딩해서 저장 |
| B | `@ai 이거 기억해`로 명시적으로 등록한 것만 지식 단위로 저장 |
| C | 채널 전체를 상시 수집하고, 분류·추출한 뒤 벡터 DB에 저장 |
| D | 따로 저장하지 않고, 질문할 때마다 메신저 검색 API로 찾기 |

한 멘토에게서는 이런 지적도 받았다.
"AI로 지식 체계(KMS)를 자동 구축하려는 시도는 역사적으로 대부분 실패했다. 조직마다 지식의 모양이 다르고 정답이 없어서, 미리 짠 분류 체계(온톨로지)는 결국 아무도 안 쓰게 된다."

## 결정

두 층으로 나눈다.

1. **원본 층**: 공개 채널에서 봇과 나눈 대화를 그대로 추가 기록한다(JSONL). 해석하지 않고, 지우지 않는다.
2. **위키 층**: 새 대화가 몇 개 쌓이면 AI가 주제별 Markdown 문서로 정리한다. 이때 규칙을 둔다.
   - 미리 정한 분류 체계 없이, 주제가 생기는 대로 문서가 생긴다.
   - 모든 사실에 **누가·어디서·언제** 말했는지 붙인다.
   - 결정이 바뀌면 덮어쓰지 않고 이전 결정을 **변경 이력**으로 남긴다.
   - 잡담이나 질문은 출처로 쓰지 않는다.

답할 때는 위키를 먼저 보고 원본을 다음으로 본다.

## 왜 이렇게 했나

- **멘토의 지적에 대한 답**: 정답 체계를 미리 설계하지 않는다. 사람이 읽고 고칠 수 있는 평범한 Markdown이 쌓이고, 출처가 붙어 있어서 AI가 틀려도 확인할 수 있다.
- **원본이 남아 있으니 위키는 언제든 다시 만들 수 있다.** 정리 방식이 바뀌어도 데이터는 잃지 않는다.
- 초안 D(검색만 하기)보다는 무겁지만, "왜 그렇게 정했는지"와 "결정이 어떻게 바뀌었는지"는 검색만으로는 안 보인다.

## 결과

- 얻은 것: 실제 모델로 테스트했을 때 잡담은 걸러졌고, "Postgres → MySQL"로 바뀐 결정이 변경 이력과 함께 정리됐다.
- 감수한 것: 위키 정리에 AI 호출 비용이 든다(새 대화 N개마다 1번). 검색은 아직 키워드 기반이라 "DB"와 "데이터베이스"를 같은 말로 보지 못한다.
- 안전장치: AI가 정한 파일 이름은 검사한 뒤에 쓴다(경로 조작 방지). AI 호출이 실패하면 해당 대화를 처리하지 않은 상태로 두고 다음에 다시 시도한다.
