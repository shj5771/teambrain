# 0003. 라이선스 경계를 구조로 지킨다

- 상태: 채택

## 상황

| 구성 요소 | 라이선스 | 성격 |
|---|---|---|
| Mattermost 서버 | 대부분 AGPL v3 | 강한 카피레프트: 수정해서 네트워크 서비스로 제공하면 수정한 소스를 공개해야 함 |
| Hermes Agent | MIT | 저작권 고지만 지키면 자유롭게 사용 가능 |
| TeamBrain | Apache 2.0 | 우리 코드 |

나중에 호스팅 서비스나 상용 버전을 만들더라도 우리 코드의 라이선스를 우리가 정할 수 있어야 했다.

## 결정

1. **Mattermost는 수정하지 않는다.** 공식 이미지를 그대로 실행하고, 공개된 REST/WebSocket API로만 통신한다.
2. **Mattermost 플러그인 형태로 만들지 않는다.** 서버 안에서 도는 플러그인은 파생 저작물로 볼 여지가 있다. 우리 코드는 항상 별도 프로세스로 돈다.
3. **Hermes 프로세스 안에서 도는 것은 괜찮다.** 처음에는 "에이전트 안에서 도는 것도 위험하다"는 해석과 "괜찮다"는 해석이 팀 안에서 갈렸다. 규칙의 원래 목적을 다시 읽어 보니, 피해야 할 것은 *AGPL 코드의 파생물이 되는 것*이었다. 에이전트(MIT)와 한 프로세스에 있는 것은 이 목적과 상관이 없었다.
4. **이름과 브랜딩에 두 프로젝트의 상표를 쓰지 않는다.** "~와 연동된다"는 사실 서술만 한다.

## 결과

- 얻은 것: 우리 코드 전체를 Apache 2.0으로 공개할 수 있고, 같은 구조로 상용화하는 길도 열려 있다.
- 감수한 것: 메신저 화면 안에 위키 버튼을 넣는 식의 깊은 UI 통합은 할 수 없다. 메신저 쪽 경험은 봇 메시지로만 만들어야 한다.
- 상용 출시 전에는 법률 전문가의 최종 검토가 필요하다. 이 문서는 법률 자문이 아니다.
