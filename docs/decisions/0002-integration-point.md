# 0002. 연결 지점은 Hermes의 메모리 플러그인

- 상태: 채택 (프로토타입으로 검증한 뒤 정식 구현)

## 상황

팀 기억 층이 대화를 "듣고"(저장) "말하게"(답하기 전에 주입) 하려면 에이전트 어딘가에 붙어야 했다.

## 검토한 선택지

| 방법 | 장점 | 탈락하거나 채택한 이유 |
|---|---|---|
| 메신저 어댑터를 새로 작성 | 흐름 전체를 직접 통제 | 이미 풀린 문제(약 1,300줄)를 다시 만들어야 하고, 메신저 API가 바뀔 때마다 대응해야 함 |
| 에이전트 코어를 포크해 수정 | 세션 개념을 마음대로 재정의 가능 | 수정할 곳이 코드 전역 십여 곳에 흩어져 있어, 업스트림이 업데이트될 때마다 병합 충돌이 남 |
| 에이전트의 외부 API 창구만 사용 | 에이전트를 전혀 안 건드림 | 메신저 리스너를 결국 또 만들어야 함. 사람별 라우팅도 불가능함(코드로 확인) |
| 이벤트 훅 | 설치가 간단 | 이벤트 내용이 500자로 잘려 오고, 기억을 주입·저장하는 API에 접근할 수 없음 |
| **메모리 플러그인(memory provider)** | 공식 인터페이스. 턴마다 `prefetch`(답하기 전 주입)와 `sync_turn`(답한 뒤 저장)이 호출되고, 채널 종류·발신자 정보도 함께 넘어옴 | **채택** |

## 결정

Hermes의 공식 메모리 플러그인 인터페이스로 구현한다. 사용자는 플러그인 폴더에 링크 하나를 걸고 설정 한 줄(`memory: provider: teambrain`)만 추가하면 된다.

## 결과

- 얻은 것: 에이전트 코드를 한 줄도 고치지 않는다. 업스트림이 업데이트돼도 잘 깨지지 않는다.
- 감수한 것: 에이전트 하나에 외부 메모리 플러그인은 하나만 켤 수 있다.
- 검증: 프로토타입으로 "한 팀원의 봇이 저장한 내용을 다른 팀원의 봇이 찾아서 답하는 것"을 실제 메신저에서 확인한 뒤 정식 구현했다.
